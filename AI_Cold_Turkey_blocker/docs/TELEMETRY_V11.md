# 采集可靠性与失联扣时 v11

本次把采集失联处理改为：**失联时间计入额度，恢复后继续使用剩余额度**。不再因为一次已计时的短暂缺口，就把整个额度时段判为不可用。

## 使用与计费

- 无法确认前台使用的清醒时间，按时间长度计入每个启用且与之交叠的额度组/时段；不知道访问了哪个应用或网站时，不捏造具体访问记录。
- 实测使用与失联扣时分开保存，界面“已用”显示两者合计，并显示包含多少秒失联扣时。CSV/JSON保留实测、扣时、估算标记和总量。
- 跨午夜和相邻时段只扣对应交集，不重复扣费。改时段、合并时段、后台重启不会清空已有扣时。
- 已确认的锁屏、空闲、睡眠及用户未登录沿用排除规则。新版保存清醒时钟锚点；同次开机、可确认没有睡眠的后台中断间隔也按失联扣时。含睡眠或旧锚点没有清醒时钟时，记录无法精确计量的原因，不把整段睡眠算成使用。
- 硬封锁、循环、倒计时、额度耗尽及时间异常仍正常限制；放宽规则仍遵守原延迟。移除浏览器组件导致浏览器保护失效时，网络兜底仍保留。采集心跳丢失期间，仍保持新鲜确认且正在前台的受管浏览器，不再仅因采集心跳缺失而立即断网。

旧版只保存了“有缺口”的标记，没有每个额度时段的精确缺失时长。迁移保留已有实测时间，按同日统计中的缺口总量作一次性保守估算，跨午夜取涉及的日期；这个值可能包含时段外缺口，因此会标注“旧记录估算”。若没有可用旧记录，以该额度上限作明确记录的估算，不能假装缺失为零。新缺口均单独计时。历史缺口标记保留作审计，不再自动代表整个时段锁死。

## 更新

关闭专注计划主窗口，双击 **更新采集与额度.exe**，点击“更新并继续使用”并完成管理员确认。适用于已安装v10的本机安装。保持持续使用，不重新开始30分钟测试；数据库、规则、例外、用量及待生效申请保留，不自动开启停用规则。

浏览器组件保持 **0.4.0**，本次无需重载。安装由用户自行操作，构建与自动检查不会修改用户正在运行的规则或策略。

## 已落实的可靠性改进

旧采集循环先同步计算应用身份哈希，再发心跳；校验变慢会拖住整条采集循环。现在单独进行后台校验，心跳不等待哈希，并使用固定节拍，避免“每轮工作耗时再加1秒”的漂移。身份仍在确认且涉及应用额度时，该段作为未确认时间计费，不静默当成免费使用。

## 新增诊断

记录客观观测，不能凭一次失联直接断言用户结束了进程。主要事件：

| 事件 | 用途 |
|---|---|
| `CollectorSessionStarted` | 采集进程、会话和起始时间 |
| `CollectorCadenceDelayed` / `CollectorForegroundSlow` | 采集循环或前台状态读取耗时 |
| `IdentityHashStarted` / `IdentityHashCompleted` / `IdentityProbeResult` | 应用文件名、大小、校验耗时及错误类型，不记完整路径 |
| `CollectorSampleFailed` / `CollectorIpcSlow` / `CollectorIpcRecovered` / `CollectorSampleDelayed` | 连接、校验服务身份、发送、读取等阶段及错误码 |
| `CollectorHeartbeatLost` / `CollectorHeartbeatRecovered` | 服务端心跳间隔、最后进程/序号/诊断、失联与恢复时间 |
| `ServicePhaseDelayed` / `AuthorityQueueWait` / `StorageCommitSlow` / `NativeOperationSlow` | 服务阶段、请求排队、数据库写入或原生策略执行是否延迟 |
| `CollectorProcessesObserved` / `CollectorTaskObserved` | 自有进程列表与任务状态；进程角色不明时明确标注 |
| `QuotaGapStarted` / `QuotaGapProgress` / `QuotaGapEnded` | 未确认区间与原因分类，实际扣款以额度记录为准 |
| `ServiceRestartGapCharged` / `ServiceRestartGapNotMeasured` / `SuspendedIntervalExcluded` | 重启或睡眠间隔是否计费及依据 |
| `LegacyGapChargeEstimated` | 旧缺口估算来源，保留实测用量 |

服务日志仍在安装目录 `state/events`；采集日志为当前用户的 `AppData/Local/AICT/beta-agent-安装ID.log`，轮转保留一份 `.previous`。日志写入不阻塞心跳，缓冲和文件大小有上限，不能保证在断电或磁盘故障时保存所有事件。通过软件“诊断与卸载 → 导出规则、用量和日志”一并导出两侧日志。

## 后续持续排查

上一次短暂失联的旧日志不足以证明具体根因。本次修正了同步哈希阻塞心跳的结构问题，仍需运行新版本观察。若再次发生，先按UTC时间、进程ID和心跳序号对应两侧日志，区分进程未运行、IPC超时、身份校验慢、服务/存储排队、睡眠恢复及仍未知的情况；根据证据增加针对性修复和回归用例，不将“已恢复”当成根因已解决。

验证回执：`reports/telemetry-v11-local-checks-20261104.json`。自动检查包含失联扣时、重复片段、跨时段、重启、旧数据迁移、导出、非阻塞校验和原有规则回归；不等于已证明所有真实环境下都不会再失联。
